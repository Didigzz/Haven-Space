# Haven Space Database Schema Documentation

## Figure 1. user_roles

The `user_roles` table serves as a lookup table for defining and managing user roles within the Haven Space system. It establishes a standardized set of roles that can be assigned to users, ensuring consistency and security across the platform. The primary key `id` is auto-incremented, providing a unique identifier for each role. The `role_name` field stores the name of the role (e.g., 'boarder', 'landlord', 'admin') and is constrained to be unique to prevent duplicate roles. The `description` field provides a detailed explanation of the role's purpose and responsibilities. The `created_at` timestamp records when the role was created, facilitating audit trails and historical tracking. This table is fundamental to the system's role-based access control (RBAC) mechanism, enabling fine-grained permission management and ensuring that users can only access features and data appropriate to their role.

## Figure 2. account_statuses

The `account_statuses` table is a reference table that standardizes the various states an user account can be in within the Haven Space system. The primary key `id` is auto-incremented, ensuring each status has a unique identifier. The `status_name` field stores the name of the status (e.g., 'active', 'suspended', 'banned', 'pending_verification') and is unique to prevent duplicates. The `description` field provides a detailed explanation of what the status entails. The `is_active` boolean field indicates whether the status allows the user to actively use the system. The `created_at` timestamp records when the status was created. This table is crucial for managing user account lifecycles, enabling administrators to control access and enforce security policies across the platform.

## Figure 3. addresses

The `addresses` table stores normalized address information for properties within the Haven Space system. The primary key `id` is auto-incremented, providing a unique identifier for each address. The `address_line_1` and `address_line_2` fields store the street address details, while `city`, `province`, `latitude`, and `longitude` fields capture the broader geographical information. The `created_at` and `updated_at` timestamps track when the address record was created and last modified, respectively. This table supports the system's property management functionality by providing a centralized and consistent way to store and retrieve address data.

## Figure 4. files

The `files` table manages file metadata for all uploaded files within the Haven Space system. The primary key `id` is auto-incremented, ensuring each file record has a unique identifier. The `file_url` field stores the URL where the file can be accessed, while `file_name`, `file_size`, and `mime_type` provide additional metadata about the file. The `file_hash` field stores a hash of the file content, enabling duplicate detection and ensuring data integrity. The `uploaded_by` field references the user who uploaded the file, and `uploaded_at` records the upload timestamp. The `deleted_at` field supports soft deletion, allowing files to be marked as deleted without being physically removed from storage. This table is essential for managing user avatars, property photos, and other file-based assets within the system.

## Figure 5. users

The `users` table is the core entity table for storing user information in the Haven Space system. The primary key `id` is auto-incremented, providing a unique identifier for each user. The `first_name`, `last_name`, and `email` fields store basic user information, with the email field being unique to prevent duplicate accounts. The `phone_number` field stores the user's contact number. The `google_id`, `google_token`, and `google_refresh_token` fields support Google OAuth authentication. The `avatar_file_id` field references the user's profile picture in the `files` table. The `password_hash` field stores the hashed password for traditional authentication. The `role_id` and `account_status_id` fields reference the user's role and account status, respectively. The `is_verified` and `email_verified` boolean fields indicate the verification status of the user and their email. The `created_at`, `updated_at`, and `deleted_at` timestamps track the user record's lifecycle. This table is central to the system's authentication, authorization, and user management functionality.

## Figure 6. properties

The `properties` table stores information about properties listed on the Haven Space platform. The primary key `id` is auto-incremented, ensuring each property has a unique identifier. The `landlord_id` field references the user who owns or manages the property. The `title` and `description` fields provide basic information about the property, while the `address_id` field references the property's address in the `addresses` table. The `price`, `deposit`, and `min_stay` fields store financial and rental terms. The `house_rules` and `gender_preference` fields define the property's policies. The `electricity_cost`, `water_cost`, and `internet_cost` fields store utility costs. The `status` field indicates the property's availability, while the `listing_moderation_status` and `moderation_status` fields manage the property's publication status. The `created_at`, `updated_at`, and `deleted_at` timestamps track the property record's lifecycle. This table is fundamental to the system's property listing and management functionality.

## Figure 7. login_attempts

The `login_attempts` table tracks failed login attempts to detect and prevent unauthorized access to user accounts. The primary key `id` is auto-incremented, providing a unique identifier for each login attempt record. The `ip_address` field stores the IP address from which the login attempt originated. The `attempts` field counts the number of failed attempts from the same IP address, and the `last_attempt` timestamp records when the most recent attempt occurred. This table supports the system's security infrastructure by enabling rate limiting and brute-force attack prevention mechanisms.

## Figure 8. landlord_profiles

The `landlord_profiles` table stores additional information specific to users with the landlord role. The primary key `id` is auto-incremented, ensuring each landlord profile has a unique identifier. The `user_id` field references the associated user record in the `users` table and is constrained to be unique to prevent duplicate profiles. The `boarding_house_name` and `boarding_house_description` fields provide information about the landlord's property. The `property_type` field indicates the type of property (e.g., 'Single unit', 'Multi-unit'). The `total_rooms` and `available_rooms` fields track the property's capacity. The `welcome_message` field stores a message that landlords can use to greet potential boarders. The `house_rules_file_id` field references a file in the `files` table containing the property's house rules. The `created_at` and `updated_at` timestamps track the profile record's lifecycle. This table extends the core user data with landlord-specific information, supporting the system's property management and tenant communication features.

## Figure 9. payment_methods_landlord

The `payment_methods_landlord` table stores payment method information for landlords, enabling them to receive payments from boarders. The primary key `id` is auto-incremented, providing a unique identifier for each payment method. The `landlord_id` field references the associated landlord profile in the `landlord_profiles` table. The `method_type` field indicates the type of payment method (e.g., 'GCash', 'Bank Transfer'). The `account_number` and `account_name` fields store the payment account details, while the `bank_name` field provides additional information for bank transfers. The `is_primary` boolean field indicates whether this is the landlord's primary payment method, and the `is_verified` boolean field indicates whether the payment method has been verified. The `created_at` and `updated_at` timestamps track the payment method record's lifecycle. This table is essential for the system's payment processing functionality, enabling secure and efficient financial transactions between boarders and landlords.

## Figure 10. payment_methods_boarder

The `payment_methods_boarder` table stores payment method information for boarders, enabling them to make payments to landlords. The primary key `id` is auto-incremented, providing a unique identifier for each payment method. The `user_id` field references the associated user in the `users` table. The `method_type` field indicates the type of payment method (e.g., 'gcash', 'bank', 'card'). The `name` field stores a display name for the payment method, and the `last_four` field stores the last four digits of the account or card number for identification purposes. The `is_default` boolean field indicates whether this is the boarder's default payment method. The `created_at` and `updated_at` timestamps track the payment method record's lifecycle. This table supports the system's payment processing functionality by providing a centralized repository for boarder payment methods.

## Figure 11. amenities

The `amenities` table stores information about the amenities available at each property. The primary key `id` is auto-incremented, ensuring each amenity record has a unique identifier. The `property_id` field references the associated property in the `properties` table. The `amenity_name` field stores the name of the amenity (e.g., 'WiFi', 'Parking', 'Laundry'). The `created_at` timestamp records when the amenity record was created. This table enhances the system's property listing functionality by providing detailed information about the features and services available at each property.

## Figure 12. rooms

The `rooms` table stores information about individual rooms within properties listed on the Haven Space platform. The primary key `id` is auto-incremented, providing a unique identifier for each room. The `room_number` and `room_type` fields provide basic identification and categorization for the room. The `property_id` and `landlord_id` fields reference the associated property and landlord, respectively. The `title` and `description` fields provide detailed information about the room, while the `price` and `deposit` fields store financial details. The `size` field indicates the room's size in square meters, and the `capacity` field specifies the maximum number of occupants. The `status` field indicates the room's availability. The `created_at`, `updated_at`, and `deleted_at` timestamps track the room record's lifecycle. This table is central to the system's room listing and management functionality, enabling landlords to manage individual rooms within their properties and boarders to browse and apply for specific rooms.

## Figure 13. applications

The `applications` table manages the application process for boarders seeking to rent rooms. The primary key `id` is auto-incremented, ensuring each application has a unique identifier. The `boarder_id`, `landlord_id`, and `room_id` fields reference the boarder, landlord, and room associated with the application, respectively. The `message` field stores the boarder's application message. The `status` field indicates the current state of the application (e.g., 'pending', 'accepted', 'rejected'). The `leave_request_status`, `leave_request_date`, `leave_request_reason`, and `intended_leave_date` fields manage leave requests from boarders. The `created_at`, `updated_at`, and `deleted_at` timestamps track the application record's lifecycle. This table is fundamental to the system's application workflow, enabling boarders to apply for rooms and landlords to review and manage applications.

## Figure 14. boarder_profiles

The `boarder_profiles` table stores additional information specific to users with the boarder role. The primary key `id` is auto-incremented, ensuring each boarder profile has a unique identifier. The `user_id` field references the associated user record in the `users` table and is constrained to be unique to prevent duplicate profiles. The `move_in_date` field stores the boarder's intended move-in date. The `created_at` and `updated_at` timestamps track the profile record's lifecycle. This table extends the core user data with boarder-specific information, supporting the system's room search and application features.

## Figure 15. platform_settings

The `platform_settings` table stores global configuration settings for the Haven Space platform. The `setting_key` field serves as the primary key and stores the name of the setting. The `setting_value` field stores the value of the setting, and the `updated_at` timestamp records when the setting was last modified. This table enables administrators to configure various aspects of the platform, such as maintenance messages, terms and privacy policy versions, and notification preferences. The settings stored in this table are used throughout the system to control platform behavior and ensure consistency across all users and features.

## Figure 16. conversations

The `conversations` table manages communication threads between users on the Haven Space platform. The primary key `id` is auto-incremented, providing a unique identifier for each conversation. The `title` field stores the conversation title, and the `type` field indicates the type of conversation (e.g., 'direct', 'group', 'welcome'). The `property_id` field references the property associated with the conversation, if applicable. The `created_by` field references the user who initiated the conversation. The `is_system_thread` boolean field indicates whether the conversation is a system-generated thread. The `created_at` and `updated_at` timestamps track the conversation record's lifecycle. This table is central to the system's messaging functionality, enabling users to communicate with each other regarding properties, applications, and other platform-related topics.

## Figure 17. conversation_participants

The `conversation_participants` table manages the participants in each conversation on the Haven Space platform. The primary key `id` is auto-incremented, ensuring each participant record has a unique identifier. The `conversation_id` and `user_id` fields reference the associated conversation and user, respectively. The `role` field indicates the participant's role in the conversation (e.g., 'member', 'admin'). The `is_active` boolean field indicates whether the participant is currently active in the conversation. The `last_read_at` timestamp records when the participant last read the conversation, and the `joined_at` timestamp records when they joined. This table supports the system's messaging functionality by tracking which users are involved in each conversation and their respective roles and statuses.

## Figure 18. messages

The `messages` table stores individual messages sent within conversations on the Haven Space platform. The primary key `id` is auto-incremented, providing a unique identifier for each message. The `conversation_id` and `sender_id` fields reference the associated conversation and the user who sent the message, respectively. The `message_text` field stores the content of the message, and the `has_attachment` boolean field indicates whether the message includes an attachment. The `is_read` boolean field indicates whether the message has been read by the recipient. The `created_at` timestamp records when the message was sent. This table is fundamental to the system's messaging functionality, enabling users to exchange messages within conversations and facilitating communication between boarders, landlords, and administrators.

## Figure 19. notifications

The `notifications` table manages notifications sent to users on the Haven Space platform. The primary key `id` is auto-incremented, ensuring each notification has a unique identifier. The `user_id` field references the user who received the notification. The `type` field indicates the type of notification (e.g., 'application_accepted', 'message', 'system'). The `title` and `message` fields store the notification's content, and the `metadata` field stores additional context in JSON format. The `is_read` boolean field indicates whether the notification has been read, and the `read_at` timestamp records when it was read. The `created_at` and `deleted_at` timestamps track the notification record's lifecycle. This table supports the system's notification functionality, ensuring that users are informed of important events and updates related to their accounts, applications, and conversations.

## Figure 20. saved_listings

The `saved_listings` table enables boarders to save properties and rooms they are interested in for future reference. The primary key `id` is auto-incremented, providing a unique identifier for each saved listing. The `boarder_id` field references the boarder who saved the listing, and the `property_id` field references the saved property. The `room_id` field optionally references a specific room within the property. The `saved_at` timestamp records when the listing was saved, and the `deleted_at` timestamp records when it was removed. The combination of `boarder_id` and `property_id` is constrained to be unique to prevent duplicate saved listings. This table enhances the system's user experience by allowing boarders to bookmark properties and rooms they are interested in, facilitating easier access and comparison during their search for accommodation.

## Figure 21. property_photos

The `property_photos` table stores photos associated with properties listed on the Haven Space platform. The primary key `id` is auto-incremented, ensuring each photo record has a unique identifier. The `property_id` field references the associated property in the `properties` table. The `photo_url` field stores the URL where the photo can be accessed. The `is_cover` boolean field indicates whether the photo is the cover photo for the property, and the `display_order` field specifies the order in which photos should be displayed. The `created_at` and `updated_at` timestamps track the photo record's lifecycle. This table is essential for the system's property listing functionality, enabling landlords to showcase their properties with high-quality images and providing boarders with visual information to aid their decision-making process.

## Figure 22. room_photos

The `room_photos` table stores photos associated with individual rooms within properties listed on the Haven Space platform. The primary key `id` is auto-incremented, providing a unique identifier for each photo. The `room_id` field references the associated room in the `rooms` table. The `photo_url` field stores the URL where the photo can be accessed. The `is_cover` boolean field indicates whether the photo is the cover photo for the room, and the `display_order` field specifies the order in which photos should be displayed. The `created_at` and `updated_at` timestamps track the photo record's lifecycle. This table enhances the system's room listing functionality by enabling landlords to showcase individual rooms with detailed images, helping boarders make informed decisions about their accommodation options.

## Figure 23. announcements

The `announcements` table manages announcements created by landlords for their properties or boarders. The primary key `id` is auto-incremented, ensuring each announcement has a unique identifier. The `landlord_id` field references the landlord who created the announcement. The `title` and `description` fields store the announcement's content, and the `category` and `priority` fields categorize and prioritize the announcement. The `publish_date` field specifies when the announcement should be published. The `view_count` field tracks how many times the announcement has been viewed. The `created_at`, `updated_at`, and `deleted_at` timestamps track the announcement record's lifecycle. This table supports the system's communication functionality, enabling landlords to share important information with their boarders and ensuring that all parties are kept informed about property-related updates and events.

## Figure 24. announcement_properties

The `announcement_properties` table establishes a many-to-many relationship between announcements and properties, enabling landlords to associate announcements with specific properties. The primary key `id` is auto-incremented, providing a unique identifier for each association. The `announcement_id` and `property_id` fields reference the associated announcement and property, respectively. The `created_at` timestamp records when the association was created. This table enhances the system's announcement functionality by enabling landlords to target their communications to specific properties, ensuring that boarders receive relevant and timely information.

## Figure 25. payments

The `payments` table manages financial transactions between boarders and landlords on the Haven Space platform. The primary key `id` is auto-incremented, providing a unique identifier for each payment. The `boarder_id`, `landlord_id`, `room_id`, and `property_id` fields reference the boarder, landlord, room, and property associated with the payment, respectively. The `amount` field stores the payment amount, and the `late_fee` field stores any applicable late fees. The `due_date` and `paid_date` fields specify when the payment is due and when it was paid. The `status` field indicates the payment's current state (e.g., 'pending', 'paid', 'overdue'). The `payment_method` and `reference_number` fields store details about how the payment was made. The `notes` field provides additional information about the payment. The `reminder_sent_at` timestamp records when a payment reminder was sent. The `created_at` and `updated_at` timestamps track the payment record's lifecycle. This table is central to the system's financial management functionality, enabling secure and efficient payment processing between boarders and landlords.

## Figure 26. password_reset_requests

The `password_reset_requests` table manages requests for password resets on the Haven Space platform. The primary key `id` is auto-incremented, ensuring each request has a unique identifier. The `user_id` and `email` fields reference the user who requested the reset and their email address. The `reset_code` field stores the code sent to the user for verification. The `expires_at` field specifies when the reset code expires. The `attempts` field tracks how many times the code has been used, and the `is_used` boolean field indicates whether the code has been successfully used to reset the password. The `used_at` timestamp records when the code was used, and the `created_at` timestamp records when the request was created. This table supports the system's authentication functionality by providing a secure mechanism for users to reset their passwords if they forget them.

## Figure 27. oauth_pending_registrations

The `oauth_pending_registrations` table manages pending registrations initiated through OAuth providers such as Google. The primary key `id` is auto-incremented, providing a unique identifier for each pending registration. The `token` field stores a unique token associated with the registration request. The `google_id`, `email`, `first_name`, `last_name`, and `avatar_url` fields store information retrieved from the OAuth provider. The `access_token` and `refresh_token` fields store the OAuth tokens provided by the provider. The `email_verified` boolean field indicates whether the user's email has been verified by the provider. The `came_from_login` boolean field indicates whether the registration request originated from a login attempt. The `expires_at` and `created_at` timestamps track the registration request's lifecycle. This table supports the system's OAuth authentication functionality by managing the intermediate state between OAuth initiation and user registration completion.
